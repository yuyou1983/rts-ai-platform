# ADR: ChatGPT 控制平面与 Hermes 执行平面

**状态：** Accepted
**日期：** 2026-08-05
**范围：** 研发侧任务分解、执行、证据提交、最终验收与回收

---

## 上下文

RTS-AI-Platform 同时包含 SimCore、运行时 Agent、Godot 前端、Harness、训练与研发侧 Skill。跨域改动通常需要多个模型或本地 Agent 连续执行。如果只传递自然语言对话，容易出现以下问题：

- 执行目标、代码基线和允许修改范围漂移；
- Agent 报告“已完成”，但没有可复跑的验证证据；
- 多个执行单元互相覆盖，或把无关工作区变更带入结果；
- 中途失败后只能重新阅读完整对话，无法从稳定检查点继续；
- 实现者的自我判断被当作最终验收，缺少独立复核。

仓库已经具备可复用的基础设施：

- `harness/skills/tasks/schema.json`：机器可读的任务 fixture；
- `harness/trace/schema.py`：执行轨迹和验证证据；
- `.agents/skills/handoff/SKILL.md`：单任务、单命令的 Agent 交接；
- `docs/agents/templates/agent-handoff-template.md`：结构化交接模板。

因此不再建立另一套任务系统，而是在现有结构上明确控制平面与执行平面的职责。

## 决策

采用以下研发编排原则：

> ChatGPT 是控制平面和路由器；本地 Hermes 是执行平面。ChatGPT 将需求拆成可独立返回的任务单元，Hermes 负责实现并完成自校验；ChatGPT 对证据、差异和关键行为进行独立复核，负责最终验收、退回和结果回收。

该原则只约束研发侧 Agent，不改变游戏运行时的四层架构，也不允许研发 Agent 绕过 protobuf/gRPC 边界。

### 角色边界

| 角色 | 必须负责 | 不得替代 |
|---|---|---|
| 用户 | 给出目标、优先级、产品判断；批准高风险或不可逆操作 | 不需要逐条指挥实现细节 |
| ChatGPT 控制平面 | 读取仓库；冻结基线；拆分任务 DAG；生成任务包；路由；处理依赖；独立终验；接受、退回或阻塞任务；汇总结果 | 不得仅根据 Hermes 的结论宣布完成 |
| Hermes 执行平面 | 读取一个任务包；按允许范围实现；保护无关变更；运行全部自校验；输出结构化结果包和证据 | 不得扩大范围、修改任务规格或自行宣布全局完成 |
| 测试与 Harness | 提供确定性、回归、架构、表现和 held-out 证据 | 不替代产品视觉判断和最终控制面判断 |

### 原子任务单元

每次 Hermes 执行只接收一个原子任务单元。一个合格单元必须满足：

1. 只有一个可观察目标；
2. 固定到明确的 `source_spec` 和 Git `fixed_point`；
3. 明确 `blocked_by`、允许路径和禁止路径；
4. 验收条件可以逐项判定；
5. 至少有一个可执行验证命令；
6. 明确证据输出和停止条件；
7. 失败或阻塞时仍能返回有效结果包；
8. 不依赖原始聊天记录才能理解。

机器可读内容优先使用 `harness/skills/tasks/schema.json`。人类和 Agent 可读的执行投影使用 `docs/agents/templates/hermes-task-unit-template.md`。

### 结果包

Hermes 无论成功、失败还是阻塞，都必须返回结果包。结果包至少包含：

- `task_id`、`agent_run_id`、起止 fixed point；
- `PASS`、`FAIL` 或 `BLOCKED` 自判结果；
- 实际修改文件和未触碰的禁止路径；
- 每条验证命令、退出码和证据引用；
- 对验收条件的逐项判断；
- 假设、偏差、残余风险和回滚说明；
- 恰好一个建议的下一条命令。

长日志不得直接复制进结果包。应保存为证据文件或记录摘要与哈希。Skill 相关执行应同时写入 `SkillTrial`，不得伪造 fresh-agent trace。

### 生命周期

```text
INTAKE
  -> DECOMPOSED
  -> READY
  -> DISPATCHED
  -> SELF_VERIFIED
  -> FINAL_REVIEW
  -> ACCEPTED | REWORK | BLOCKED
  -> RECOVERED
```

- `SELF_VERIFIED` 只表示 Hermes 完成了执行者自校验。
- 只有 ChatGPT 可以把任务置为 `ACCEPTED`。
- `RECOVERED` 表示结果已被汇入总计划、报告、后续任务或版本提交范围。
- `FAIL` 产生修复任务；`BLOCKED` 记录外部依赖和恢复条件，均不得伪装成完成。

### 最终验收门禁

ChatGPT 在接受任务前必须独立完成以下检查：

1. **规格门：** 结果与 `source_spec` 和验收条件一致；
2. **范围门：** diff 只覆盖允许路径，没有覆盖用户的无关变更；
3. **证据门：** 验证命令、退出码、产物和运行标识完整且可追溯；
4. **复跑门：** 至少独立复跑风险最高的验证；关键共享行为需扩大回归范围；
5. **架构门：** 四层依赖、协议边界和领域规则没有漂移；
6. **产品门：** Godot 操作、资源、动画或 VFX 变更必须有运行时截图或人工检查项，headless check 不能替代视觉验收；
7. **回收门：** 把接受的结果映射回总计划，并明确未完成项、后续任务和提交边界。

Hermes 的 `PASS` 是终验输入，不是最终结论。

### 并发与冲突

- 只有 `blocked_by` 为空且写路径不重叠的任务可以并发。
- 修改共享协议、核心状态模型或同一 Godot 场景的任务默认串行。
- ChatGPT 负责分配所有权和合并顺序；Hermes 不自行领取相邻任务。
- 发现 fixed point 变化、禁止路径需要修改、规格矛盾或无关工作区污染时，Hermes 必须停止并返回 `BLOCKED`。

### 权限与安全

破坏性 Git 操作、外部网络下载、依赖安装、资产许可变更、凭据使用和不可逆数据迁移仍需用户授权。任务路由不得把授权责任转移给执行 Agent。

本地 Hermes 默认使用可保留审批边界的 `chat --query --checkpoints`。不得把会自动绕过危险命令审批的 `--oneshot/-z` 或显式 `--yolo` 设为项目默认分发方式。

## 后果

### 正面

- 每次执行可独立复现、失败、重试和回收；
- Hermes 可以批量承担局部实现，ChatGPT 保持全局架构和验收一致性；
- 执行者自证与控制面终验分离，降低错误完成声明；
- 任务 fixture、SkillTrial、handoff 和现有 Harness 得到统一使用。

### 成本

- 小任务也需要固定点、验收条件和结果包；
- ChatGPT 需要保留终验时间，不能把所有验证下放；
- 视觉与操作手感类任务仍需要人工证据，无法完全自动化。

## 未采用方案

1. **让 Hermes 自主拆分并最终验收：** 执行与审计同源，容易扩大范围并遗漏全局冲突。
2. **ChatGPT 直接完成所有实现：** 无法充分利用本地 Hermes 的批量执行能力，控制面被实现细节占满。
3. **只使用聊天记录交接：** 缺少固定点、可执行命令和结构化证据，无法稳定恢复。
4. **为编排另建新的任务数据库：** 与现有 task fixture、SkillTrial 和 handoff 重复。

## 验证方式

该决策通过以下可观察条件验证：

- 每个被分派任务都有一个通过 `harness/skills/tasks/schema.json` 校验的 fixture，或等价的任务单元文档；
- 每次 Hermes 返回都包含结构化结果包，不论结果状态；
- `PASS` 任务存在 Hermes 自校验证据和 ChatGPT 独立终验证据；
- 多任务执行可以仅凭任务包、结果包和仓库证据恢复，不需要复制聊天记录；
- 最终总结明确区分 `ACCEPTED`、`REWORK` 和 `BLOCKED`。
