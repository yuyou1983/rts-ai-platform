# Skill Harness Bounded-Context Glossary

> Owner: **harness-executor** (cross-cutting)
> Scope: skill trials, candidate patches, traces, auditors, held-out suites, promotion.
> Permitted dependencies: observes all layers; promoted patches cannot mutate runtime business code.

---

## SkillTrial

Definition: a single execution of a skill candidate against a defined task,
producing a trace, evidence, and a verdict that feeds the promotion pipeline.

Not the same as: a one-off script run, which may produce output but is not
governed by trace validation, auditor checks, or held-out evaluation.

Boundary example: running a skill in a terminal and observing "it works" is
not a SkillTrial — a SkillTrial requires a recorded trace, validation
commands executed, and auditor verdicts captured.

---

## Candidate Patch

Definition: a proposed change generated by a skill during a SkillTrial, held
in a sandboxed location and not yet applied to the codebase, that must pass
validation and held-out evaluation before Promotion.

Not the same as: a committed change, which has already been merged into the
repository baseline and is no longer a candidate.

Boundary example: a skill produces a patch that adjusts a Godot shader
parameter — the Candidate Patch sits in the trial directory; it becomes a
committed change only after Promotion with explicit `--apply` and manual
approval.

---

## Silent Bypass

Definition: a failure mode in which a skill's declared behavior or validation
requirement is present in its instructions but never appears in the execution
trace, meaning the skill was loaded but its discipline was not exercised.

Not the same as: a skill that runs and fails, which produces a visible error
in the trace and is therefore not silent.

Boundary example: a skill's instructions say "must run determinism tests" but
the trace contains no pytest invocation — the skill was loaded, the rule was
stated, but validation was silently bypassed.

---

## Held-out Trial

Definition: an evaluation run of a Candidate Patch against task fixtures and
data the skill has not seen during development, used to detect overfitting and
confirm generalization before Promotion.

Not the same as: the development trial, which uses the same fixtures the
skill was developed against and therefore cannot detect overfitting.

Boundary example: a skill passes all development trials but fails a Held-out
Trial on a different map seed — this indicates the skill overfit to the
development seed and must not be Promoted.

---

## Promotion

Definition: the act of accepting a Candidate Patch as the new repository
baseline, requiring explicit `--apply` flag, manual approval, and a passing
Held-out Trial — never automatic or silent.

Not the same as: applying a patch during a SkillTrial, which is a dry-run
test of the patch and does not change the baseline.

Boundary example: a Candidate Patch passes all validation and held-out
checks — it is still not Promoted until a human runs the promotion command
with `--apply` and confirms; automated "auto-promote on pass" is forbidden.

---

## Trace

Definition: the structured, append-only record of every tool call, decision,
and validation result produced during a SkillTrial, used by the auditor to
verify that the skill's declared behavior was actually exercised.

Not the same as: a log file or stdout capture, which may be informal and
is not structured for auditor verification.

Boundary example: a skill's Trace shows Read, Write, and Bash calls with
timestamps and arguments; if the Trace shows no validation command despite
the skill requiring one, the auditor flags a Silent Bypass.

---

## Auditor

Definition: the automated checker that inspects a Trace against the skill's
declared expected tool calls, validation commands, and known failure modes,
returning a structured verdict before Promotion is considered.

Not the same as: a code linter, which checks source quality independently of
whether a skill was actually invoked or its discipline was followed.

Boundary example: an Auditor verifies that a skill declaring "must check
manifest" actually contains a Read call for the manifest in the Trace — a
linter would only check that the code references a manifest, not that it was
read during the trial.

---

## SkillEvolver

Definition: the system that generates multiple Candidate Patches for a skill,
runs each as a SkillTrial, compares their evidence, and proposes the best for
Held-out Trial and Promotion — the sole path from candidate to baseline.

Not the same as: a manual edit, which bypasses the trial, held-out, and
comparison process and therefore cannot serve as promotion evidence.

Boundary example: a developer manually edits a skill and commits — this is a
valid code change but is not a SkillEvolver run and provides no promotion
evidence for the held-out pipeline.
